### 各点検項目

- デフォルトブランチはAPIで `main`。workflowはmainにあり、cronのUTC前日23:00/23:15/23:45はJST 08:00/08:15/08:45に正しく対応。
- `if: github.ref == 'refs/heads/main'` はpush/schedule共通。取得した実行はmainをcheckoutし、テスト・ビルド・検査・アップロード・deployがすべて成功している。
- `contents: read`、`pages: write`、`id-token: write` を維持。実行された3件に権限エラーはない。
- workflowの有効状態の管理APIは利用可能な接続では取得できず、08時時点の有効/無効の履歴も未確認。10:54以降のschedule成功は、その時点で定時実行が機能していた証拠。前日にもmain更新・成功runがあり、60日無活動による自動無効化を示す根拠はない。
- concurrencyは既存の `group: pages` / `cancel-in-progress: false`。記録のある各runは作成から3〜4秒でbuildを開始し、キャンセルなし。08時台の記録がないため、GitHub内部でrun作成前に何が起きたかは不明。記録のあるrunに長時間のconcurrency待機があったとは言えない。
- `publishedTimestamp` は `2026-11-08T08:00:00+09:00`（UTC 11/7 23:00）。セレクターは実時刻の `COLUMN_BUILD_AT` と比較し、未来記事を除外する。既存日時判定の修正は不要。

## 実装した再発低減策

1. 08:00開始のcronを07:50 JST（UTC前日22:50）へ移動。GitHub公式が注意喚起している毎時00分の起動集中を避ける。08:15・08:45の再試行は維持し、workflow起動は引き続き1日3回。
2. 準備・テスト後、07:50のrunだけ実時計が08:00になるまで最大10分待機する。**未来の08:00をCOLUMN_BUILD_ATへ先に設定しない**。遅れて08:00以降に開始した場合は直ちに実時計でビルドする。push・手動実行は待機せず、従来どおり現在時刻で公開対象を絞る。
3. event・元のcron式・開始時刻・待機秒数・ビルド基準時刻をログへ記録し、次回はcron枠とrunを対応付けられるようにする。ジョブtimeoutで既存のPagesロックを無期限に占有しない。
4. 既存の生成HTML検査を維持し、期限到来記事の欠落・未来記事の混入を公開前に止める。
5. Pagesデプロイ後、実サイトのトップ・一覧（ページ送りを含む）・sitemap・最新記事個別ページ・その関連記事を読み取り照合。期待値は**照合時点の実時計**から算出し、公開時刻直前の古いビルドを誤って合格させない。反映・通信遅延に備え10秒間隔で最大3回確認し、失敗時はdeployジョブを失敗にする。フォーム送信・JavaScript実行なし。
6. build/deployの結果とcutoffを常時実行のstatusジョブでまとめ、失敗をActionsの失敗状態・エラー・Summaryとして表示する。新しい通知先・有料サービスは追加しない。GitHub側の失敗通知設定が必要であり、通知先・受信は今回未確認。

記事本文・画像・公開日時・URL・デザイン・SEOの変更はない。

## 11/9以降の見込み・残存リスク・復旧
