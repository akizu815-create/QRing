- 空の自治体一覧は自己canonical＋noindex,follow。公開自治体記事が入ればindexへ切替え、サイトマップにも追加。静的再ビルドが必要。
- 既存2記事を `src/content/columns/published.json` の構造化ブロックへ移行。タイトル・導入・全10セクション・全段落・リスト・リンク・表・出典を維持。公開日は既存の2026年10月27日を保持し、移行日を内容更新日にしていない。
- 既存2本の固定page.tsxを削除し、`[slug]` の `generateStaticParams` で同じ2URLを生成。固定・動的ルートの二重定義なし。`dynamicParams=false`、Next.js 15の非同期paramsに対応。
- 一覧・記事・サイトマップで共通の公開抽出関数を使用。非公開状態・未来公開を除外。新規記事は本文リビジョンと承認リビジョンの一致、未解決の主張・不合格検査がないことを検査。欠落・不整合時はビルドを止める。
- 記事データは本文HTML/JSXとして実行せず、許可した段落・リスト・リンク・表だけを描画。一覧クライアントには公開カード情報だけを渡す。
- 目次、カテゴリー・主読者、出典別確認日、関連記事、canonical・OG・Article/BreadcrumbのJSON-LDを追加。既存記事のSEOタイトル・descriptionは維持。
- 自治体サービスページから自治体コラム一覧への内部リンクを追加。問い合わせURLは既存の `https://axb.qring.jp/contact` を維持。
- 更新管理用の確認日・次回確認日・サービス仕様版を保存。ローカルCLIで期限到来、出典90日経過、指定した仕様版との不一致を一覧化可能。

初期2本には `publicationOrigin: existing` を用い、過去に公開されていた事実を引き継ぐ。初期リビジョン1だけを移行例外とし、それ以降のリビジョンは新規記事と同じ承認条件を通す。新たに管理者が承認したという履歴を創作しない。これは新規記事の承認を省略する機能ではない。公開済みJSONは公開リポジトリに置くため、実際の下書き・承認情報・秘密情報は絶対に入れない。

## 第2段階：スマートフォン承認画面

認証後の一覧は「確認待ち」「要修正」「更新が必要」の3つを基本とし、一覧カードでタイトル・読者・出典確認状態・検査失敗数・予定日を表示。タップで完成表示を開き、本文／出典／検査結果を切り替えられる構成とする。

下部に「修正」「差し戻し」「承認」を配置し、44px以上のタップ領域を確保する。「承認」は重大な未確認・検査失敗がある間は無効。差し戻しは定型理由＋任意コメント、修正は本文と主要メタの編集・保存。本文・出典等が変わればサーバー側でリビジョンを増やし承認を失効させる。承認時のリビジョンを提示し、競合更新は上書きせず再読込を促す。

承認と公開実行は別の状態とし、管理者承認がない記事は公開用リポジトリへ渡さない。完全自動公開は品質検証完了後、ユーザーの明示的承認でのみ有効化できる設定として監査記録を残す。現在はその設定やUIを作っていない。

## 第2段階：費用の概算と上限

2026年11月5日確認の参考価格。モデルは未採用であり契約・課金設定は行っていない。品質検証で採用モデルとプロンプト・消費量を確定してから実額を再見積もりする。

| 区分 | 第1段階 | 第2段階の考え方 |
|---|---|---|
| 新規契約の初期費用 | なし（新規有料契約をしていない） | 利用サービス決定後に確認。開発委託費・既存契約料金とは別 |
| 追加月額固定費 | 新しい有料サービスを追加していない | 非公開DB・認証・バックアップのプラン次第。無料枠内なら追加0円の可能性、未契約なので確約しない |
| 従量費 | AI生成APIの呼出しなし | モデル入出力、検索回数、実行・ストレージ等 |
| 1記事の試算 | 対象外 | 下記の仮定で約23円、3倍の処理量なら約68円（税・為替手数料等を除く） |
| 月30本の試算 | 対象外 | 同じ仮定で約675円、3倍なら約2,025円＋固定費等 |

例としてGPT-5.4 miniの標準入力$0.75/100万token、出力$4.50/100万token、Web search $10/1,000回を用いる。企画・執筆・検査を合計して入力60,000token（検索内容分も含む）、出力10,000token（課金される推論tokenも含む）、検索6回なら、`0.06×0.75 + 0.01×4.50 + 6×0.01 = $0.15/記事`。仮定の1ドル150円で22.5円。これは現在の為替・実測消費量ではなく比較用の前提。画像生成、追加外部検索API、再実行は別計算。単価の安さだけでモデルを決めない。

出典：
- https://developers.openai.com/api/docs/models/gpt-5.4-mini
- https://developers.openai.com/api/docs/pricing

上限案（未設定・要承認）：月3,000円、日150円、1記事100円。月次は日本時間で区切る。管理画面に当月実績・実行中予約額・残額・失敗回数を表示。外部APIの請求ダッシュボードの予算通知だけをハード上限とみなさない。

実装では各リクエスト前に最大入力・出力・検索回数から上限費用を算出し、非公開DBで原子的に予算を予約する。実行中予約額も残額から控除し、上限に達したらAPIを呼ぶ前に保留。実行後はusageで精算。不明な結果・通信切断は使用額不明として予約を保持し、機械的な再送を止める。単価表に版・確認日を付け、モデルが変わる場合に自動で安い想定を流用しない。

ジョブ単位の一意制約、日付＋制作目的の実行キー、ロック、有効期限、全工程で共通の試行カウンターを設ける。1日1本、同時実行1件、ジョブ全体の自動再試行は最大2回、指数バックオフ。検査不合格を無制限再執筆するループは禁止。人の再試行も同じ費用台帳・上限を通す。

## 第2段階：毎日生成の重複防止

生成主体は1つに限定する。現在は既存のChatGPT毎日原稿作成タスクを維持し、このPRでは別のcronやAPIジョブを作らない。サイトが参照するのは公開済みデータだけであり、ページ閲覧やビルドを原稿生成のトリガーにしない。

サイト側パイプラインへ移行するときは、旧タスク停止・実行中ジョブ確認・新パイプライン有効化を一つの切替手順とし、同時稼働させない。タスク停止などの設定変更は別途明示して実施する。ChatGPTタスクから原稿を自動取得できる連携は未確認なので、利用可能と仮定しない。

制作台帳では日本時間の日付・企画ID・生成実行IDを一意管理し、再実行や別トリガーでも同じ企画を二重発行しない。公開の冪等キーは記事ID＋承認リビジョンとし、生成の重複防止とは別に管理する。
