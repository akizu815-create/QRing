# 既存GSCを活かすSEO編集支援：追加実装と接続手順

2026年11月5日。基準は `column-implementation-plan-20261105.md` の全11章と追加決定、`column-phase1.md`。コラム基盤とその承認・静的出力・デザイン・費用管理の要件を維持する。

## 最新の補足を優先した範囲

Google Search Console自体は既に利用されている。GSCと同じ分析画面は作らない。公開Next.jsサイトにもSEO管理画面やGoogle認証処理を追加しない。

編集支援の出力は「次に作るべき記事」「改善すべき記事」「改善理由」を基本とする。詳しい数値は根拠データとして保持し、GSCへの確認に使う。日常操作を増やさず、将来の認証付き承認画面へ提案キューを接続する。独立したWeb管理サーバーや二つ目の承認システムは作成していない。

既存 `scripts/gsc-report.mjs` の引数なし実行（上位10クエリ表示）は維持し、`--sync` オプションで必要な取得・保存だけを追加した。既存の `GoogleAuth` とサービスアカウント方式を再利用する。既存GSCのデータがないという判断ではなく、この実行環境で認証設定が確認できない状態である。

## データの保管とアクセス制限

追加の管理DBが既存リポジトリに存在しなかったため、非公開のSQLiteを最小のアダプターとして用意した。既存の公的GSC環境を置き換えるDBではない。デフォルトはgit対象外の `.qring-private/seo.sqlite`。実行ユーザーのみが読める親ディレクトリと600のファイル権限を要求し、src/public/out内への配置を拒否する。私的な数値・検索クエリ・提案・利用記録はリポジトリへコミットしない。

将来承認バックエンドが決まったら、次のテーブル契約をそのDBへ移せる。現時点でSupabase等の外部DB作成・課金・権限変更は行っていない。

| テーブル | 用途 |
|---|---|
| `gsc_runs` | 成功・失敗と時刻、機密情報を含めないエラーコード |
| `gsc_slices` | property・日・集計種別ごとのデータ、集計単位、取得時刻、上限到達フラグ |
| `gsc_exports` | 既存CSVの期間とフィルター、粒度、インポート履歴（CSV利用時作成） |
| `proposals` | AI入力・根拠・修正提案・リビジョン・承認待ち状態 |
| `usage_ledger` | 実行中費用予約、実績、不明額、日・月の上限計算 |
| `changes` | 記事変更と28/56/90日の変更前ベースライン |
| `reports` | 分析結果と編集アクションの再利用・履歴 |
| `article_snapshots` | 将来の公開イベントから記事内容の版を記録するための予約テーブル。現在の自動入力なし |

公開HTTPエンドポイントを追加していないため、今回のCLIは許可された実行環境・OSユーザーからのみ利用する。スマートフォンからのアクセスは、認証付き編集画面へ統合してから提供する。Private DBをそのままWeb配信しない。

## GSC入力の使い方

既存のGSC表示：

```sh
node scripts/gsc-report.mjs
```

認証済み環境で日次確定データを同期：

```sh
npm run seo:sync
```

初回の28日比較には前期間も必要。少量ずつ取得し、通常は直近7日だけを実行する。

```sh
npm run seo:sync -- --days 60 --max-calls 500
npm run seo:sync -- --days 190 --max-calls 1500
```

- `GOOGLE_APPLICATION_CREDENTIALS` は既存のサービスアカウントキーのパスを非公開環境へ設定する。既存の認証情報が使える場合は新しいアカウントを作らない。キー本体をチャット・公開コード・src・publicへ貼らない。
- `sc-domain:qring.jp` に対する読み取り権限とSearch Console API有効化を確認する。既存アカウントの権限設定を勝手に変更しない。
- APIスコープは `webmasters.readonly`。APIキーによる私的GSCデータ取得はしない。
- 直近10日の確定済み日別データから取得可能な最新日を判定。GSC日付のAmerica/Los_Angelesを使用。前日分が必ず存在するとは仮定しない。
- site/device/page/query/page_query/page_deviceを分離し、サイト集計とページ集計を混ぜない。
- 25,000行ずつページ送りし、50,000行到達を上限到達として記録。取得できた行を全クエリとみなさない。
- 既取得の過去日をスキップし直近3日は再取得。1実行120 API呼出しが初期値、明示指定で最大2,500。429/5xxだけ最大2再試行。ロックで同時実行を防ぐ。
- 失敗した同期バッチでは既存のデータを変更しない。ロック残存は稼働中ジョブを確認してから解除し、機械的に消さない。
- 取得・AI処理をサイトのビルドや公開の前提にしていない。失敗しても通常のサイト公開は続けられる。

既存GSC CSVを利用（エクスポート時の正確な期間を指定）：

```sh
python3 -m scripts.seo_ops.cli import-csv --csv /private/gsc/Pages.csv --start 2026-10-05 --end 2026-11-01
python3 -m scripts.seo_ops.cli import-csv --csv /private/gsc/Queries.csv --start 2026-10-05 --end 2026-11-01
```

ページで絞り込んだクエリCSVの場合だけ `--page-filter https://www.qring.jp/column/elderly-monitoring/` のように、実際に指定したフィルターを付与する。サイト全体のクエリを個別記事の流入と扱わない。CSVがqring.jpのエクスポートであること、検索タイプ・デバイス等のフィルターを管理者が確認する。今回のインポートはWeb検索・全デバイスの基本集計を対象とし、その他のフィルターやZIP/XLSXの直接入力は未対応。CSVの期間内訳は保持するが、CSV同士の直積から日付×ページ×クエリを生成しない。API入力がない場合だけCSVの同一期間スナップショットを分析に使う。

## 日常的に見るもの

```sh
npm run seo:actions -- --format md
npm run seo:actions -- --period 7 --kind weekly --format md
npm run seo:actions -- --period 28 --kind monthly --format md
```

Markdownは3つの編集判断に絞る。`--format json` には詳細な根拠・取得日・欠損状況・指名/非指名の観測値・デバイス・カテゴリ・想定読者・公開時期区分を含める。日次API入力では7日・28日・90日・暦3/6か月を同じ根拠から集計する。`kind monthly` は現在28日レポートの保存区分であり、暦月前月比較は未実装。月次と28日比較を同一と説明しない。

数値集計・記事候補抽出は通常のプログラムで行う。指名語は正規化したQRing/キューリング/つながるQR等。既知クエリを指名と非指名に分け、秘匿・欠損を非指名に含めない。CTRは合計クリック÷合計表示、順位は表示回数で加重平均。比較対象が不十分な場合に独自の標準CTRを作らない。

公開直後（28日未満）・観測不足・取得上限到達は保留。同カテゴリーと順位帯の比較対象が3本以上ある場合にAの相対CTRを検討。B/D/Eは前期間が取得済みで公開56日以降の変動を検討する。Cは確認できる露出が少ないときの調査候補とし、インデックス未登録・検索需要なし・品質不良を断定しない。CSVモードは日別と同じ判定精度があると説明せず、期間集計で確認できるD等に限定する。

テーマ候補は実際の非指名クエリを根拠とし、内容に関する語・記事台帳との類似性から、改善と新規調査を分ける。類似度は初期の簡易検出であり、同じ検索意図を完全に判定する機能ではない。需要・競合・季節性・制度の変化は別途調査が必要なものとして示し、月間検索数を創作しない。既存記事・関連公式サービスのリンク案は公開済み記事と存在を確認できるページに限定し、自動挿入しない。

## 任意AI分析：承認待ちの修正案のみ

有料実行は現在無効。実行にはAPI利用の明示的承認を得たうえで、非公開実行環境へ `OPENAI_API_KEY`、`QRING_SEO_AI_ENABLED=true`、`QRING_SEO_AI_APPROVAL_ID` を設定する。キー・承認情報は公開サイトへ渡さない。認証設定や有料契約を今回変更していない。

```sh
python3 -m scripts.seo_ops.cli analyze-ai --article elderly-monitoring
```

データ不足なら有料APIを呼ばず保留。入力した記事・実績・プロンプト版・モデルのハッシュで結果をキャッシュし、同じ根拠の再生成を避ける。原因、推奨タイトル、推奨description、本文修正案、追加情報、内部リンク案、出典、期待する方向性を構造化して保存する。外部調査を行うアダプターではないため、競合・最新制度・導入効果等を確認済みとして出力しない。出典は入力記事で確認済みのURLだけを受け入れる。内部リンクは許可した公開記事・存在する関連ページのパス以外を拒否する。リンクの文脈上の適切さと本文事実は認証付きレビュー時の追加検証が必要。

結果は `proposals.status=review`、本文版と承認版は別で保持。公開記事のファイルへ書き込む処理は存在しない。既存計画のスマートフォン承認画面へ、元記事・修正案・SEO根拠・出典を渡す契約とする。認証付きUI・差分の実表示・承認後の反映は、既存の承認機能が実装された段階で接続する。CLIを承認システムの代わりにはしない。

費用はリクエスト前に最大入力byte数＋余裕、最大出力6,000tokenから保守的に予約。SQLiteの排他トランザクションで当月・当日実績＋未確定予約を控除する。初期のアプリ内上限は月$5・日$1（設定値、AIは無効）。外部請求アラートをハード上限とはみなさない。タイムアウトや不正な応答は費用不明として予約を残し、同じ分析の自動再送を禁止する。未知の処理結果をリトライして二重請求を生むことを避ける。単価改定や採用モデル変更時はコード内の単価と予約計算を再確認する。

## 改善効果の記録・比較

記事の変更を実際に承認・反映した後、管理側の公開イベントから次を呼ぶ設計。現在はCLIによる明示記録に限定する。承認前の提案を、反映済みの変更として記録しない。

```sh
python3 -m scripts.seo_ops.cli record-change --article elderly-monitoring --changed-at 2026-12-01 --before-revision 1 --after-revision 2
npm run seo:effects
```

変更直前28/56/90日を固定保存し、変更日から同じ期間の取得が揃うまで比較を保留。比較値は因果的な改善効果と断定しない。制度改正・季節性・アルゴリズム・同時の別修正等は別途確認する。CSVだけの比較はここでは未対応。成功パターンの自動学習・次回プロンプトへの自動反映は未実装で、確認済みパターンのレビュー後の取り込みが次段階となる。

## 追加費用の整理

新規有料契約なし。公開サイトの固定費・デプロイ設定を変更しない。GSCの取得・通常集計は既存APIとローカル処理を使用し、AIのAPI料金は発生させていない。将来の私的な常時実行環境・バックアップ・認証基盤の費用は採用先決定後に確認する。開発工数・委託費は以下のAPI原価とは別。

追加AI分析の試算：GPT-5.4 mini標準入力$0.75/100万token、出力$4.50/100万token（2026年11月5日確認）。1分析で入力10,000・出力4,000tokenなら$0.0255。仮定の$1=150円で約3.8円。外部検索・画像生成・追加の再分析を含まず、実測値や現在の為替ではない。モデル選定・品質検証後に再試算する。

| 月の新規記事数 | 新規記事API費（既存計画の約22.5円/本の仮定） | 任意の改善分析数 | 改善分析の追加試算 | 合計参考 |
|---:|---:|---:|---:|---:|
| 15本 | 約338円 | 8回 | 約31円 | 約368円 |
| 30本 | 約675円 | 8回 | 約31円 | 約706円 |
| 60本 | 約1,350円 | 16回 | 約61円 | 約1,411円 |

毎日全記事をAIに送らず、数値上の調査候補や管理者が選んだ記事だけを分析する。新規生成と改善分析で別々に無制限な上限を作らず、将来は共通費用台帳へ統合する。今回の台帳は全purposeの当日・当月額を合計できる構造。

## 管理者が操作する事項

1. 既存Google API用認証を、安全な実行環境へ引き継ぐ。必要な場合だけGSC読み取り権限・API有効化を確認する。新しいGSCプロパティやダッシュボードを作る必要はない。
2. 必要であれば既存GSC CSVを非公開で指定する。Google認証情報をチャットへ貼る必要はない。
3. 継続実行するバックエンド・私的DBの保存先とバックアップ先を確定する。既存の承認バックエンドを作る際に共用する。
4. 有料AIを使う場合のみモデル・月額上限・API利用を承認する。それまでは数値候補・テーマ候補の通常集計を利用可能。
5. 日次同期・週次/月次レポートを既存ジョブへ統合する際に実行時刻と閲覧先を設定する。今回、既存毎日原稿タスクや自動化設定を変更していない。
6. 本番マージ・公開は引き続きユーザーの事前承認後に行う。完全自動公開も品質検証と明示承認を必須とする。

## 検証・受入基準

`npm run test:seo-ops` で外部通信のない合成データを使用。未取得/null、重み付き順位・CTR、指名正規化、匿名クエリの分離、同期失敗時の保持、CSV粒度、公開時期による保留、候補D、重複警告、AI無効時の無課金、予算上限、キャッシュ、タイムアウト再送防止、承認待ち保存、効果比較の保留、静的ディレクトリへのDB配置拒否を検証する。

加えて `npm run build`、既存 `test:columns`、`check:column-export`、SEO監査を実行し、公開サイトの挙動と記事データが従来どおりであることを検証する。実GSCのAPI取得、CSV実ファイル、実AI応答・請求、常時実行・スマートフォンの認証/承認、GA4・問い合わせ完了については実接続の受入が別途必要。合成データの成功を実データ接続済みと説明しない。
