# HOME画像配信・問い合わせ導線・GA4の確認（2026年10月31日）

対象：`https://www.qring.jp/`、`akizu815-create/QRing`。基準コミット：`8d13e719c7bf91fb966f8cc2da8d47a23fdfe373`。

## 今回実施した修正

- HOMEの既存PC・スマートフォン用PNGから、同じ解像度のAVIF・WebPを作成。元のPNGは保持した。
- `HeroVisual.tsx`を1つの`picture`にし、767px以下は既存モバイル写真、768px以上は既存PC写真を選択する。AVIF → WebP → PNGの順で対応形式を選択する。
- 構図、画像の表示枠、`object-fit`、モバイルの`object-position: 52% center`、グラデーション、粒子表現を維持。拡大・縮小・切り抜き・色調補正は画像生成時に行っていない。既存のCSSによる表示時のトリミングも維持した。
- 高齢者ページのdescriptionを「身につけたQRコードを発見者がスキャンし」に修正。title・canonical・URL等は維持。共有設定を使用するOG description・WebPageのdescriptionも一致して更新される。
- 旧`/contact/`の「法人プラン・API連携・大量導入・ホワイトラベル展開のご相談」を、現行公開フォームと同じ「法人・自治体での導入、実証実験、複数のQRコードのご利用など、お気軽にご相談ください。」に修正した。未確認の提供内容を案内し続けないための文言整理であり、機能や契約条件を変更したものではない。
- 問い合わせフォームの削除・転送、送信先、GA4設定、料金・サービス仕様・利用規約は変更していない。本番公開・mainへのマージは行わない。

## 画像ファイルと実配信

| 用途 | 解像度 | 元PNG | WebP | AVIF | AVIFの元PNG比削減率 |
|---|---|---:|---:|---:|---:|
| PC | 1586 × 992 | 2,263,259 bytes（約2.16MiB） | 266,930 bytes（約261KiB） | 241,924 bytes（約236KiB） | 89.3% |
| スマートフォン | 941 × 1672 | 2,010,334 bytes（約1.92MiB） | 177,366 bytes（約173KiB） | 156,600 bytes（約153KiB） | 92.2% |

変更前の本番画像をHTTP GETで取得し、`Content-Type: image/png`、上記の実バイト数、リポジトリ内PNGとのSHA-256一致を確認した。Next.jsは静的出力（`output: "export"`）かつ`images.unoptimized: true`で、実配信もPNGそのままだった。`sizes="100vw"`だけでは解像度別・形式別の画像は生成されていなかった。

変更前はPC・モバイル用に別々の`Image`と`priority`があり、非表示側を含め両PNGが取得された。変更後はブラウザーが画面に合う1枚を選択する。ChromeでAVIFの選択を確認し、AVIF sourceを除いた比較用コピーでWebPフォールバックも確認した。PNGは旧形式向けのフォールバックとして残している。

生成条件：既存のSharp、WebP quality 92 / effort 6 / smartSubsample、AVIF quality 85 / effort 6 / chromaSubsampling 4:4:4。RGB・元のピクセル寸法を維持。局所Gaussian SSIM（sigma 1.5、RGB平均）による参考比較はPC AVIF 0.98809 / WebP 0.98220、モバイル AVIF 0.98438 / WebP 0.97538。画質指標だけで合否を決めず、PC・スマートフォン幅の画面で顔・布地・QRタグ・文字との重なりを目視比較した。大きな画質劣化や構図変更は認めなかった。

## 表示速度への影響

同じ静的配信環境の変更前後コピーをChromeで比較。回線・CPU制限なし、DPR 1、CSS・フォントはウォーム、画像はデバイス・形式・回ごとに別クエリを付けてキャッシュを分離した。比較用コピーではReact・GA等のスクリプトを除去し、同一条件の初期HTML描画をPerformanceObserverで測定。各回でload後1.5秒の完了信号を待ち、LCP・CLS・Resource Timingを記録した。計測コードは本番出力・リポジトリへ追加していない。

LCP要素は各回HERO画像だった。PCはウィンドウ1363×936（ページ有効幅1348）、画像表示1348×898.656px。スマートフォン相当は390×844のiframe（スクロールバーを除く幅375）、画像表示375×764px。変更前後の表示寸法・位置は一致した。実機・高DPR端末の検証とは異なる。

これは検証環境の参考値であり、本番サイト全体のLighthouseスコアやユーザー実測Core Web Vitalsの改善率ではない。初回試行にはフォント・画像キャッシュや描画完了前の読み取りによる揺れがあったため、上記は条件を揃えた3回比較の値を記録した。PageSpeed Insights APIはHTTP 429（利用枠超過）で取得できず、CrUX・Search Consoleのウェブに関する主な指標は未取得。公開後は同じURL・同じ測定条件で再測定し、実ユーザー指標は必要な集計期間を置いて評価する。

## 窓口統一案

第一候補は`axb.qring.jp/contact`。現在の主要CTAも既にこのURLであるため、今回新たなリンクの付け替えは不要。

1. Formspreeと現行APIについて、通知先・保存先・担当者・受付履歴・障害時の確認方法を管理画面／運用担当者と照合する。現行フォームの成功・失敗・確認メール・管理者通知を、承認済みテストで検証する。
2. Search ConsoleのURL検査・検索パフォーマンス・リンクレポートで、旧`/contact/`の登録状況・流入・外部リンクを確認する。今回旧ページを削除・noindex化・転送せず、canonical・sitemapも維持した。
3. 現行フォームの稼働・計測が確認できた後、まず旧ページ内に現行窓口への案内を置くか、旧フォームを廃止して転送するかを決める。旧フォームの受付がある場合は取りこぼしがない移行期間を設ける。
4. 恒久移行を決める場合、ホスティング側のHTTP 301/308を利用できるか確認し、旧URLの直接アクセス・クエリ・外部リンク・canonical・sitemapをまとめて整備する。GitHub Pagesの静的出力でNext.jsのサーバーredirectを設定するだけでは実現しないため、JavaScript転送をHTTP転送と混同しない。

## GA4：確認できたことと不足事項

| 項目 | 公開コード・DOMで確認できた範囲 | 追加確認・対応案 |
|---|---|---|
| 公式サイトのタグ | `layout.tsx`に`G-M75FF9RHJ6`のgtag読み込み・configが1組 | 実際の受信・同意設定・フィルターはGA4管理画面で確認 |
| CTAクリック | 明示的な問い合わせクリック用イベント実装なし | 拡張計測のclick設定は未確認。同一親ドメイン間の移動を自動の外部クリックに依存しない。必要なら`contact_cta_click`を配置名と送信先のみで計測 |
| フォームへの到達 | 公式サイト側のクリックだけでは到達を証明しない | axbのpage_view等で`/contact`の実到達を確認する |
| axbのタグ | 初期HTML、公開コアJS・問い合わせJS、表示後DOMでGA測定ID・GTM・Google解析scriptを確認できなかった | タグが絶対に存在しないとは断定しない。別経路のタグ／サーバー計測も含め、axb管理者・GA4で照合 |
| 送信完了 | 現行API成功時にモーダル表示する実装はあるが、対応するGA4完了イベントは確認できない | 成功応答が確認できた処理で一度だけ`generate_lead`等を記録。エラー・送信ボタン押下・form_submitだけを問い合わせ完了にしない |
| サブドメイン間 | 同じ親ドメインだが、両サイト同一タグ・cookie_domain・client/session IDの継続は未確認 | cookieの有効範囲、データストリーム、必要なドメイン設定、自己参照を確認。同じ親ドメインというだけで継続を保証しない |
| 流入元・参照元 | HOME・SERVICE・自治体・コラボ・ヘッダー・フッター等のCTAは`rel="noopener noreferrer"`で新しいタブを開く | noreferrerは参照元を送らない指定。Cookieによる継続とは別の問題。運用方針確認後にnoopenerを残してnoreferrerを外す案を検討し、外部広告用UTMを内部移動に付けて流入元を上書きしない |
