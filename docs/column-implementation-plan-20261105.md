## 1. 維持する方針と今回の追加範囲

既存サイトのデザインと実装基盤、毎日1本の記事生成、初期の承認制から将来の完全自動公開への移行方針を維持します。読者を「個人・家族」「自治体・公共機関」「企業・施設」の3層へ拡張し、カテゴリーとは別に記事の想定読者を管理します。

自治体向けでは、地域課題・既存施策・運用上の検討事項を優先します。QRingの紹介は文脈上必要な場合の選択肢にとどめ、実証や相談につながる実用的な情報メディアを育てます。

記事ごとに主カテゴリー1つと主読者1つを必須にします。補助タグは任意です。例えば「高齢者・認知症」カテゴリーにも自治体向け記事を登録できます。「自治体・地域課題」だけを自治体向けとみなす実装にはしません。

- `/column/{slug}/`：記事の唯一の正規URL。読者ごとに本文を複製しません。
- `/column/audience/municipal/`：自治体・公共機関向け記事の編集付き一覧。カテゴリーを横断して抽出します。
- カテゴリー一覧・他の読者一覧は記事数に応じて静的生成。内容が薄い一覧は検索対象にする必要性を見直します。
- 絞り込みクエリの組み合わせは無制限にインデックスさせず、canonicalとindex方針を整理します。
- 既存2記事のパスを予約し、動的ルートの生成対象と重複させません。新テンプレートへ移行する場合も同一URLを維持します。

一覧はカテゴリー名・想定読者・タイトル・要約・公開日を読みやすく表示。記事には目次、更新日、参考資料、関連する記事を配置します。既存の余白・書体・配色を継承し、装飾や営業用バナーの増設を避けます。スマートフォン、キーボード操作、見出し階層も確認します。

## 4. 記事データと下書き管理

既存計画にデータ形式・保管先がある場合はそれを優先します。未確定なら、公開記事を検証可能なJSONまたはMarkdownで保持し、共通テンプレートから静的出力する方式を推奨します。AIが生成したTSXや任意の実行コードをビルドに取り込まない構成にします。

| データ | 用途 |
|---|---|
| `id`, `slug`, `title`, `summary`, `body` | 記事識別・表示 |
| `category`, `primaryAudience`, `tags` | 7カテゴリーと3読者層の独立管理 |
| `status` | draft / review / approved / scheduled / published / needs_revision / archived |
| `metaDescription`, `canonical`, `relatedArticleIds` | 検索結果表示・内部リンク |
| `publishedAt`, `updatedAt`, `reviewedAt`, `nextReviewAt` | 公開・更新・再確認管理 |
| `searchIntent`, `primaryKeyword`, `topicClusterId` | 企画・重複防止 |
| `sources[]` | 出典名、発行主体、URL、公表・更新日、確認日、該当箇所 |
| `claims[]` | 制度・数値等の主張と対応する出典ID、確認状態 |
| `cta` | none / contextual / municipal、文脈に合う案内 |
| `contentRevision`, `approvalRevision`, `validationResults` | 承認後の変更検知、検査結果 |
| `generationRunId`, `promptVersion` | 再実行の重複防止・生成履歴 |

公開リポジトリであるため、未承認本文を公開ブランチや公開PRへ置いて秘匿扱いにはできません。下書き・承認画面は既存計画の認証付き保管先を用い、未確定なら非公開の保管先を採用します。公開用リポジトリへ渡すのは公開対象の記事だけにします。

承認画面では完成表示、読者・カテゴリー、出典と該当記述、重複候補、検査結果をまとめて確認できるようにします。下書きは公開用out、サイトマップ、公開JSON、検索対象に含めません。noindexだけをアクセス制御に使わないでください。

## 5. 自治体向け記事の編集基準

基本の検討順序は、①地域社会の課題、②国・自治体の関連施策、③現在の対応方法、④既存施策の課題・検討事項、⑤新技術・仕組みの活用可能性、⑥導入・実証時の検討事項、⑦参考資料・出典とします。テーマごとに比較、事例解説、チェックリスト、実証設計等へ構成を変え、同じ見出しを機械的に繰り返しません。

- 制度名・対象地域・対象者・年度・受付期間は国や自治体の公式資料で確認します。全国制度と一自治体の制度を区別します。
- 本文の重要な制度説明・数値の近くに出典を示し、末尾にも資料名・発行主体・URL・確認日を掲載します。URLが開けることだけで根拠確認済みにはしません。
- 確認できた事実、課題の分析、導入仮説を区別します。QRingの採用・推奨・効果測定を裏付ける資料がなければ、そのような表現は使用しません。
- QRingの自治体導入、実証成果、費用削減、発見率向上、連絡時間短縮等を創作しません。他社・他自治体の成果をQRingの成果へ転用しません。
- 既存施策を一律に否定せず、利用条件、運用体制、できること・確認事項を客観的に比較します。競合の名指し比較を前提にしません。
- QRingをGPS、常時追跡、異常自動検知、緊急通報の代替として説明しません。発見後の連絡を支える役割を正確に扱います。
- 個人情報に関する記事は公式資料を根拠とし、「番号非公開なので個人情報上の検討は不要」などと断定しません。本人の意思、情報の共有範囲、保管・権限・削除等を検討項目として扱います。
- 架空の監修者・専門資格・体験談は掲載しません。編集主体と制作方針を明示し、人が確認した範囲を事実どおりに表示します。

GoogleもAI利用時の正確性・品質・関連性を重視し、価値を加えない大量生成に注意を促しています。[7] 毎日1本は生成の基本であり、品質未達の日に無理に公開するノルマにはしません。

## 6. テーマ選定・生成配分・重複防止

初期は30本で個人15本・自治体9本・企業6本を目安にします。日々の並びを固定せず、公開済み記事と制作中企画の両方を参照し、直近30本の主読者の不足、検索意図、季節性、情報更新、社会的関心から選定します。配分と対象期間は設定で変更可能にします。既存2記事は分類して管理し、新規30本の生成割当とは分けて数えます。

重複検査はタイトル一致だけでなく、対象読者・読者の課題・検索意図・結論・本文類似性を比較します。同一意図なら既存記事の更新を優先します。読者だけを変えた内容の薄い類似記事は増やしません。

各企画には、想定キーワード、検索意図、検索結果の種類、既存記事との差分、一次資料、独自に追加する比較表や検討項目を記録します。検索数を取得できない場合は未取得と記載します。公開後はSearch Consoleの実際の表示・クリック・クエリを利用して優先順位を更新します。

## 7. 自動化と公開制御

生成処理は「企画選定→一次資料取得→構成→執筆→主張と出典の照合→重複・仕様・リンク・表示検査→公開判定」とします。失敗時は公開せず、理由と次の対応を記録します。再試行は同じ実行IDを用い、二重公開を防止します。

### 初期：承認制

毎日1本を下書き化し、確認画面で承認・差し戻し・修正・公開日時指定を可能にします。承認はその本文リビジョンに結び付け、本文・出典等の変更で無効化します。予約時刻に未承認または検査失敗なら公開を見送ります。

### 移行後：完全自動公開

既存計画の移行方針を維持します。切替条件は、重大な事実誤認ゼロ、出典照合・重複判定・本文修正時の承認失効・失敗時の公開保留・公開停止と復旧が検証済みであることとします。自動モードでは検査に合格した記事を人の個別承認なしで公開し、未検証の制度・数値・効果等が残る記事は保留します。経過日数や記事数だけでは切り替えません。

公開方式にかかわらず、次を実装します。

- 生成モードと公開モードを分離し、自動公開をいつでも止められる設定。
- 公開直前に本文リビジョンと検査結果を再確認。
- 静的記事・一覧・サイトマップを同一ビルドで更新。
- ビルド失敗時は既存公開版を保持し、成功時だけpublishedへ遷移。
- 公開後のURL・本文・canonical・サイトマップ・内部リンク確認と、前バージョンへ戻す手順。
- APIキー・認証情報は公開ファイルやブラウザコードへ含めない。

既存のGitHub Pages配信に合わせ、生成処理とビルド・配信を連携します。GitHub Actionsの標準トークンによる自動pushで通常のpushワークフローが再実行されると仮定しないでください。既存デプロイ処理を共通化するか、明示的なディスパッチ等を採用し、生成から公開まで実際の発火を検証します。具体方式は既存権限と運用を確認して確定します。

## 9. 成果測定

記事台帳の正規URL・記事IDと `primaryAudience` を基準に集計します。「自治体向けの記事が読まれたこと」と「実際の読者が自治体職員だったこと」は区別します。アクセス情報から所属を推測して断定しません。

| 指標 | 計測方法案 | 制約・注意点 |
|---|---|---|
| 記事別表示回数・検索クリック・CTR・掲載順位 | Search Consoleのページ別データを記事台帳と結合 | 想定読者は記事メタデータから付与 |
| 検索キーワード | ページ・クエリ別データを別途取得 | 匿名化等により全キーワードは取得できず、合計が一致しない場合あり |
| CTA利用 | GA4の明示的な `contact_cta_click` | 記事ID、主読者、カテゴリー、配置を送信。クリックを問い合わせ完了としない |
| 問い合わせフォーム到達 | axb側のページ表示または到達イベント | フォーム側対応の有無を確認。クリックだけで到達済みとしない |
| 問い合わせ完了と記事の関係 | API成功時の `generate_lead` と記事IDの連携 | フォーム側の実装が必要。送信ボタンや汎用form_submitでは代用しない |
| 問い合わせ内容から見た実際の読者層 | フォームの申告区分を集計 | 記事の主読者と別項目。個人情報をGA4に送らない |

Search Consoleはページやクエリでの取得に対応していますが、全行の取得は保証されません。[8] ページ別合計とページ×クエリ内訳を分けて保持し、欠落や日付基準を記録します。

まず記事側のクリック計測とSearch Console集計を実装し、フォーム側の対応ができた段階で送信完了まで連携します。未連携の間は「問い合わせ完了：未計測」と表示し、ゼロと混同しません。

フォーム側対応時は、同一データストリーム・Cookie有効範囲・セッション継続を確認し、必要に応じたドメイン間設定を行います。同じ親ドメインなので必ず継続するとは仮定しません。[9] 記事ID等の個人を含まない流入情報をフォームへ引き継ぐ方式を検討し、既存の送信処理を壊さず検証します。内部移動への広告用UTMの付与は避けます。

GA4に氏名・電話番号・メール・相談本文等を送信しません。流入記事は原則として直近の記事CTA経由で記録し、初回接点も扱う場合は別項目・別の集計定義にします。重複送信防止と、どの時点を「問い合わせにつながった」と判定するかを明文化します。

月次集計は3読者層を同じ条件で比較し、記事ごとの検索表示・クリック・CTA利用・計測可能な完了数と、テーマ別の傾向を確認します。検索と問い合わせを個人単位で直接結び付けられると説明しません。

## 10. 実装手順と受入条件

| 段階 | 実装内容 | 完了判定 |
|---|---|---|
| 1 | 既存コラム・SEO・配信構成の照合、記事データ設計 | 既存URL・見た目の継承方法、7カテゴリー、3読者層が定義済み |
| 2 | 一覧・記事・読者別一覧、既存記事の分類 | カテゴリーと読者の組合せで正しく絞り込める |
| 3 | 認証付き下書き・承認・生成・各種検査 | 未承認・将来公開・検査失敗の記事が公開出力されない |

受入確認では、既存2URLの維持、読者横断の抽出、未承認本文の非公開、根拠不足・架空実績の公開ブロック、承認後修正の失効、静的ビルド、SEO情報の重複なし、問い合わせ先の一致、PC・モバイル表示、イベント二重送信なしを確認します。フォームへの実送信はこの計画の受入に必須とせず、必要な場合はテスト環境で検証します。
