# Phase 2：動画・購入登録導線の設計（未実装）

調査日：2026年11月7日。現行Next.js 15の静的exportと、既存の画像・HERO・CTA・料金・決済・マイページを維持する。以下は検討案であり、動画プレーヤー・購入CTA・計測イベント・新規ページは実装していない。

## 1. 約30秒の紹介動画

### 推奨方式と掲載位置

初期案は、**既存配信先での自社ホスティング＋ネイティブvideoのクリック再生**。30秒の承認済み動画が軽量に用意でき、現行ホスティングの容量・転送条件に収まることを前提とする。条件未確認のまま新サービスや有料ストレージを追加しない。

HOMEは既存How it worksの3ステップ末尾にコンパクトなサムネイルと再生操作を置く案を推奨する。HEROには置かず、独立した長い新セクションを増やさない。SERVICEはHow to Useの見出し下、登録者／発見者タブの上に同じ動画を置く。詳細手順の代わりにはしない。サムネイルの横に長い説明や機能一覧を重ねない。

将来の共通コンポーネントは同じ動画IDまたはasset URL・poster・字幕・文字起こし情報を参照し、HOMEとSERVICEで文言・動画を別管理しない。配置サイズのみ変える。ビルド時に固定素材を出力し、再生の状態だけ小さなClient Componentで扱えるため、静的exportの維持が可能。サーバーAPIや新しい依存ライブラリは不要。今回はコンポーネントを追加しない。

| 観点 | 自社ホスティング／video | YouTube埋め込み |
| --- | --- | --- |
| 上品な表示 | ブラウザ標準controlsを利用。自社画面内で完結 | 外部プレーヤーのUI・ブランド等を完全には取り除けない |
| 初期読み込み | ローカルposterのみ。動画はpreload=none、必要ならクリック時にsrcを設定 | ローカルposterを置き、クリックまでiframe・外部サムネイル・APIを読み込まない |
| 負荷 | 転送量・容量・コーデック・キャッシュは自社側で確認 | 初期の外部JS負荷をクリック後へ遅らせる。広告・外部通信等の仕様は確認が必要 |
| 管理 | 動画差し替え・字幕・配信ヘッダーを管理 | 既存の正式チャンネル、動画の権限・埋め込み許可の確認が必要 |
| モバイル | playsInline、controls、適切な字幕。端末実機確認が必要 | プレーヤーの最小サイズとcontrolsの表示領域を確保 |
| 判断 | 30秒・容量が許容される場合の第一案 | 既存チャンネルの利用が承認され、外部配信を選ぶ場合の第二案 |

YouTubeを選ぶ場合は、プライバシー強化モードのyoutube-nocookie.comを検討する。ただし「外部通信・広告・追跡が完全になくなる」とは説明しない。modestbranding等の廃止されたパラメータに依存しない。自動再生は設定しない。公式の最小viewportは200×200pxであり、狭い画面で16:9だけを機械的に当てると高さ不足になり得る。例えば幅335pxでは高さを最低200px以上に予約し、controlsと字幕の見やすさを実機で確認する。HTTP Refererを抑止すると再生が失敗する場合があるため、公開配信時のヘッダーも確認する。

### 読み込みとアクセシビリティ

- プレーヤーの表示領域は先に寸法を予約し、再生開始で周辺の文章を押し下げない。サムネイルをLCP対象のHEROより先に高優先で読み込まない。
- ネイティブvideoはpreload=noneを基本にし、読み込み制御をvideoのloading属性対応だけに依存させない。JavaScriptを使えない場合は標準controlsまたは承認済み動画URLへの通常リンクと文字起こしを用意する。
- 再生は実際のbuttonで行い、名前は「つながるQRの紹介動画を再生（約30秒）」等にする。Enter/Space、フォーカス表示、停止・再開・音量・字幕を利用できるようにする。自動再生・自動ループを前提にしない。
- 字幕は動画への焼き込みだけで済ませず、日本語WebVTTと文字起こしを用意する。映像だけに重要情報がある場合は、それを把握できるナレーション・代替説明も必要。
- 375/390/430pxとPC、iOS Safari／Android Chromeで字幕・controls・縦横切替・通信失敗を確認する。クリック前に動画・外部プレーヤーが要求されないことをネットワークログで確認する。

### 別途必要な素材・承認

承認済みMP4（H.264/AAC等の端末対応を確認）、poster、字幕WebVTT、文字起こし、表示タイトル・再生時間、映像・音声・人物・楽曲の使用許可。WebMは必要性と容量を見て追加判断する。動画構成・画像・字幕の制作や編集は今回行っていない。

自社配信ではファイルサイズ・Content-Type・Range対応・キャッシュ・転送量を実配信で確認する。容量の目安は素材受領後に画質を見て合意し、劣化の強い圧縮を先に決めない。素材確定前のVideoObjectや架空の再生時間・公開日も追加しない。

参考：[web.devの動画遅延読み込み](https://web.dev/articles/lazy-loading-video)、[MDN track/WebVTT](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/track)、[YouTubeプレーヤー仕様](https://developers.google.com/youtube/player_parameters)、[埋め込み・字幕・プライバシー強化モード](https://support.google.com/youtube/answer/171780?hl=ja)。閲覧した仕様を根拠にした案であり、現サイトでの実装・測定結果ではない。

## 3. 正式リリース後の推奨導線

入口（HOME／コラム／活用ページ）→サービスと料金→QRの入手方法→必要な場合のみ購入→専用QRから登録→初期設定完了、という分岐を提案する。すでにQRを持つ人には購入を強制せず、持っていない人には入手方法を先に案内できることが望ましい。ただし、販売・配布の実仕様を確認してから確定する。

将来の「つながるQRをはじめる」は、既存SERVICEのGet Startedと活用ページ末尾、HOMEのサービス説明の末尾を候補にする。HEROを変更する前提にはしない。既存CONSUMER_SERVICEで準備中案内とCTAを共通管理しているため、提供開始時の案内変更をそこへ集約し、HOME等の追加位置も同じ設定から参照する案とする。今回は設定値・CTAを変更していない。

直接登録がQR識別情報を必要とする場合は、「はじめる」を未確認の汎用フォームへ直結しない。「QRをお持ちの方／入手したい方」の案内先を、実在し承認されたURLへ確定してから設定する。新規ページの要否も販売形態の確定後に判断する。

### 離脱を抑えるための確認候補

現時点の実測による離脱原因ではない。入手方法が見つからない、購入後に登録手順へ戻れない、購入者と登録者を混同する、QRスキャンで別ブラウザへ移る、入力エラーから復帰できない等がないかを確認する。

公開前に、同意を得た検証環境・テスト用QRで、iPhone／Androidの新規・既存利用者、戻る／再読込、入力エラー、認証がある場合の期限切れ、購入がある場合の成功・失敗・重複操作まで検証する。現時点で不要な登録項目や決済条件を勝手に削除しない。

サービス概要の段階で「通話成立時のサービス利用料」と「通常の電話料金」「アイテム代金」を区別し、購入を伴うなら注文確定前、登録では最終確認前に実際の適用条件を確認できる設計を推奨する。価格・免除条件・支払期限の値自体は既存案内を維持し、販売条件が決まるまで新たな確約をしない。
