## 配信先に関する重要な区別

取得したmainのrun 46121256491は **Deploy to GitHub Pages** で成功し、既存の本番検証先は `https://www.qring.jp/`。#185はこの既存経路を維持する。Cloudflareで確認できたのは **qring-preview** のGit連携によるブランチプレビューであり、本番Cloudflare Pagesへの定時デプロイ経路はリポジトリにない。

したがって「Cloudflare Pagesへの本番自動再配信が確認済み」とは扱わない。Cloudflareが実際の本番配信元であれば、Pagesプロジェクト・本番ブランチ・カスタムドメイン・ビルド設定・デプロイ方式を管理画面で確認し、現行のGitHub Pages配信との関係を確定するまで本番稼働完了としない。Cloudflareへの切り替えは本PRに含めず、必要になれば別途設計と承認を得る。

新しい認証情報・契約・外部サービスは、**確認できているGitHub Pages経路**の修復には不要。Cloudflare本番が必要な場合のhookや認証要否は未確認であり、不要と断定しない。

## 推奨する承認・マージ順序

1. 代表者が#185の修復内容と、別の予約原稿PRの**2記事第2版・画像・SEO・予定日時**をレビューする。本書作成時点では承認未了。
2. 管理画面で本番配信元、Pages環境保護、schedule許可、GitHub失敗通知の受信設定、利用枠を確認する。古いworkflowの実行／待機があれば担当者が確認・整理する。本作業では変更・キャンセルしない。
3. 承認後、まず#185をmainへマージ。pushの新workflowがplan→必要時build→deploy→本文検査まで成功することを確認する。
4. 予約原稿PRを最新mainへ付け替え、競合・全CI・既存28記事の不変を再確認する。代表者が承認したコミットの予約設定だけをmainへマージする。承認フィールドはPR内の適用案であり、Draft作成自体を承認の証拠にしない。
5. 29日08:00 JSTより前にマージできた場合は、29・30日のルート・本文・一覧・XMLが非公開であることを確認する。日時を過ぎてからマージした場合は、実時計ですでに到来した記事が次の処理で公開対象になる。過去へ時計を戻したり、無断で予定日を変更しない。
6. 以後は毎日のコミット・マージ・公開フラグ変更は不要。必要時の手動操作は、初回の管理画面確認、承認した2PRのマージ・付け替え、稼働受け入れ、障害時のworkflow_dispatchだけ。
