## 3. 配置境界と認証連携

公開GitHub Pagesに置くのは、引き続きNext.jsが出力する `out/` のみです。`scripts/editorial/`、DB、下書き、抜粋、認証設定を `src/`・`public/`・`out/` にコピーしないでください。管理サーバーは別の非公開実行環境が必要です。既存の公開サイトをサーバー構成へ変更していません。

ローカルの合成データ検証用：

```sh
npm ci
python3 -m scripts.editorial.server --development --port 8765
```

`--development` は127.0.0.1固定で認証を省略しローカル全権限を与える、明示的な開発専用モードです。このポートを外部公開・転送しないでください。実データと共有しない検証用DBは `--db` で指定できます。通常起動はdevelopmentフラグを付けません。

通常配置は、既存のログイン基盤を前段に置く方式が利用可能かを確認してから行います。現時点で当該基盤が利用可能とは断定していません。非公開環境にのみ以下を設定します。

| 設定 | 用途 |
|---|---|
| `QRING_SEO_DB`（CLI）またはserverの`--db` | 既存SEOと共有する永続SQLite。親ディレクトリ0700、ファイル0600。ソース・公開出力下は禁止 |
| `QRING_EDITORIAL_ORIGIN` | 管理画面の正確なHTTPS Origin（末尾スラッシュを含めない） |
| `QRING_EDITORIAL_PROXY_SECRET` | 前段プロキシと共有する32文字以上の秘密値。ブラウザ・公開リポジトリに置かない |
| `QRING_EDITORIAL_ROLES` | 認証済みactor→`viewer` / `editor` / `reviewer` / `publisher` の配列を持つJSON。現場の権限に合わせて設定 |

プロキシは既存認証の本人確認後、クライアント由来の `X-QRing-*` ヘッダーを全除去し、毎回新しいnonceと時刻を生成します。次の6項目を改行で連結し、UTF-8・HMAC-SHA256の小文字hexで署名します。

1. actor
2. Unix秒の時刻文字列
3. リクエストごとのnonce
4. HTTPメソッド
5. アプリに渡すpath（クエリを含む）
6. アプリに渡すbody bytesのSHA256 hex（GETなら空バイト列）

`X-QRing-Actor`、`X-QRing-Time`、`X-QRing-Nonce`、`X-QRing-Signature` として渡します。許容時差60秒、nonce再利用拒否。静的管理UIのGETを含む全アクセスが認証対象です。POSTは正確なOriginとJSON必須、CORSを許可しません。TLS終端と管理サーバーを同じホスト／安全なloopback経路に置き、サーバーの直通公開をしません。通常起動にはproxy secret・actorロール・HTTPS Originが必要です。認証基盤・署名プロキシは今回配置していません。

## 4. 生成の運用と費用

現状維持の経路は、既存8時タスクの原稿を運用担当者が構造化パケットに整え、非公開CLIへ渡す方法です。ChatGPTタスクから自動取得する連携は未確認です。

```sh
python3 -m scripts.editorial.cli plan --actor OPERATOR
python3 -m scripts.editorial.cli import --actor OPERATOR < PRIVATE_PACKET.json
python3 -m scripts.editorial.cli usage --actor OPERATOR
python3 -m scripts.editorial.cli runs --actor OPERATOR
```

`PRIVATE_PACKET.json` は公開リポジトリ外に置きます。importは `{ "article": Article形式, "evidence": [...] }`。evidence要素は `sourceId`、`url`、`checkedAt`（YYYY-MM-DD）、`excerpt`（20文字以上の原文抜粋）、`kind`（`primary`または`trusted`）です。新規記事のID・slug・検索意図・キーワード・クラスタを必須とし、既存記事は別途改訂下書き作成を使います。sourceIdはarticle.sourcesおよびclaimsと対応付けます。importもAI生成も同じ日付一意台帳を通るため、その日の記事がある場合は追加生成せず編集します。本文HTML／JSXは受け付けません。

API生成への切替はまだ実行していません。次を事前に確認・承認してから、1つの生成主体に切り替えます。

- 実際に使う既存の有料API契約・モデル単価・利用上限。
- 既存8時タスクの停止と処理中ジョブの確認。新旧を並行稼働させない。
- 調査済み原文・仕様パケットを日々供給できる経路。未検証のWebページをAIが閲覧済みとみなさない。
- 非公開ジョブ実行環境、バックアップ、エラー通知先。今回cron・通知・契約は追加していない。

API生成の設定は `QRING_COLUMN_AI_ENABLED=true`、`QRING_COLUMN_AI_APPROVAL_ID`、`QRING_COLUMN_PRODUCER=pipeline`、`QRING_COLUMN_CUTOVER_APPROVAL_ID`、非公開 `OPENAI_API_KEY` です。いずれも今回設定していません。既存のSEO分析承認だけでは新規記事生成は有効になりません。

```sh
python3 -m scripts.editorial.cli generate --actor WORKER < PRIVATE_RESEARCH_PACKET.json
```

研究パケットは `keyword`（GSC候補がない場合）、`sources`、`evidence`、`serviceSpecification`（確認済み仕様のversionと内容）を持ちます。出力は承認なしのdraftです。既存SEOのモデル・入出力単価定数を参照し、価格版名をtoken台帳に記録します。**今回の実測料金ではありません。** 導入前に契約側の価格を確認し、既存分析への影響も評価してください。

共通上限は既存の `QRING_SEO_AI_MONTH_USD` / `QRING_SEO_AI_DAY_USD`（未指定時は既存コードと同じ月5USD・日1USD）です。既存分析と新規生成の合計で制限し、外部請求額・税・為替・旧ChatGPTタスクの利用額は含みません。通信切断等では予約を残します。精算済みの不正結果のみ `--retry` で最大合計2試行。請求不明のときは、実行終了と請求元の実際のtoken数を確認し、以下で照合してから手動で再実行判断します。照合コマンド自体は再実行しません。

```sh
python3 -m scripts.editorial.cli reconcile --actor OPERATOR --run-id RUN_ID --input-tokens N --output-tokens N --reference PROVIDER_REQUEST_REFERENCE
```

すでに下書きが保存されていればその下書きに復旧し、重複生成しません。

## 5. 公開準備から本番反映まで

1. 管理画面で記事を修正・確認し、確認記録を付けて記事承認。変更があれば確認・承認は失効する。
2. publisherが対象の承認リビジョンを選び公開準備。元の公開データと対象版のハッシュを非公開台帳へ保存。
3. 運用担当者が `python3 -m scripts.editorial.cli export --actor OPERATOR --release-id RELEASE_ID` を実行。元データの変化と承認失効を再検査し、DB隣接の非公開 `releases/` へ書き出す。公開データは直接変更しない。
4. 今後、レビュー用の別Git作業ブランチへ当該承認スナップショットを取り込み、既存記事の差分・URL・公開対象・本文・出典をレビューする。静的ビルドと下記公開出力検証を実行し、対象コミットを確定する。
5. **記事承認とは別に、そのコミットの本番マージ／デプロイについて管理者の明示承認を得る。** 未承認のままmainへpush／mergeしない。
6. 承認後に限り、既存main push→GitHub Pagesの仕組みを利用する。今回そのworkflow・公開設定は変更していない。

自動コミット、main push、PRマージ、workflow dispatch、デプロイを行うコードは追加していません。スナップショットのGit取込・本番実行・実デプロイ結果の自動取得は未接続です。画面は「リポジトリの公開用スナップショット」と「実際の本番反映」を区別し、本番状態を推定で公開済みにしません。
